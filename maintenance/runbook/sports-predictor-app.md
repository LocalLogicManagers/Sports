## Design system (as of the "tech/AI, gambling picks for nerds" redesign)
Both `index.html` and `ravens.html` share one design language — a dark-leaning "terminal/data" aesthetic, deliberately distinct from mainstream sports-betting sites (e.g. Pickswise) while covering the same functional ground (games/picks/odds nav, per-sport tabs, expert-style reasoning replaced by transparent model math).
- **Typography:** Space Grotesk (headings/display), IBM Plex Mono (data, labels, nav indices, `//`-comment-style section headers), IBM Plex Sans (body copy).
- **Motifs:** terminal-prompt brand mark (`>_`), `$ `-prefixed eyebrow lines, `//`-prefixed section titles, numbered primary-nav tabs (`01 Picks`, `02 Horses`, `03 Track Record`, `04 Odds & Bets`), a subtle CSS grid-line background, glow/box-shadow accents on active/hover states, monospace pill badges.
- **Color tokens** (full palette in both files' `:root` / dark-mode blocks): `--home` (blue), `--away` (red-orange), `--good` (green), `--warn` (gold/amber), `--off` (cyan-teal, used for offseason/neutral status), `--pick` (violet, the site-wide accent). `ravens.html` adds `--ravens` (purple, `#5B2AA8` light / `#9E7BE0` dark) as its page-specific accent, used the way `--pick` is used site-wide. All were validated with the dataviz skill's `validate_palette.js` against the color groups that actually appear adjacent in the UI (home+away in game bars; good+warn+off in status-pill dot sequences; pick/ravens+off in badges) — not a blanket all-pairs check, since those tokens are never rendered as a single shared legend.
- **Do not** revert to the old Oswald/olive-green v1 palette — this redesign superseded it per explicit user request.

## What it does
- **Picks, not just probabilities.** Every game gets an explicit winner pick + confidence tier (Toss-up/Lean/Moderate/Strong for team sports; Wide-open/Lean/Moderate/Strong favorite for horse racing, tiered by ratio to a fair 1/N field share).
- **Every pick is logged before the contest happens**, then graded once the result is known, and rolled into a public Accuracy Tracker / "Track Record" tab (overall hit rate, per-league accuracy, Brier score, calibration by confidence tier, home/away and favorite/underdog splits).
- **The model self-calibrates**: a bounded coordinate-search nudges each sport's home-advantage/sigma constants toward whatever would have minimized Brier score on that sport's own graded history so far. Requires a minimum sample (default 25 graded games) per sport before it's allowed to move, and steps are small (≤0.5 home-adv, ≤1.0 sigma per run) — gradual, not volatile.
- **Win probabilities are capped at [3%, 97%]** (`engine.win_prob(..., cap=0.97)`) so lopsided matchups (e.g. ranked-vs-unranked NCAAF) don't produce absurd implied odds like -8000. Keep this cap if you touch `engine.py`.
- **Wager Calculator ("Odds & Bets" tab):** two tools, both with stake + currency (USD/EUR/GBP/CAD/AUD/JPY) inputs computed client-side in JS (mirrors `engine.py`'s odds math exactly — `DEFAULT_VIG=0.045`, `fair_prob_to_vig_prob`, `prob_to_american_odds`, `american_to_decimal`, `parlay_decimal_odds`). (1) **Bet slip** — checkbox list of every currently-open pick; Singles mode defaults all-checked (each a separate bet), Parlay mode defaults **none checked** (a parlay should be a deliberately hand-picked few legs, not the entire day's slate — this was a bug fix, don't revert the default) and shows a combined-hit-probability warning above 8 legs. (2) **Historical bankroll simulator** — flat-stake backtest over the graded log, Singles or Parlay-by-day. Odds shown are clearly disclosed as **modeled, not live sportsbook lines** (simulated standard-vig line from the model's own probability) except horse racing, which uses real posted morning-line odds.
- **Horse racing** (major US thoroughbred races only, per user's scope choice): model = morning-line odds → implied probability → normalized across the field (overround removed). Pick = highest resulting probability. No speed figures/trainer-jockey stats yet — free full past-performance data isn't available; upgrade path is a paid feed (Equibase/DRF/TVG) if the user wants to provide one later.
- **Leagues:** NFL, MLB, EPL, MLS, PLL Lacrosse, NCAA Football (AP Top 25 scope), NBA, NCAA Basketball, UEFA Champions League.
- **Baltimore Ravens sub-page (`ravens.html`):** a dedicated deep-dive, same model/methodology, covering: a **"Should I bet on the Ravens this week?" verdict card** (see below), Super Bowl odds + history table, full 18-week schedule with per-week Ravens win probability (bar chart) and value-bet notes comparing model probability to real market odds where available, a **bet-call track record**, offseason roster-changes (departures/acquisitions), preseason standouts/concerns, and a collapsible full roster by position group.

### "Should I bet on the Ravens this week?" verdict + track record
The most-requested feature on the Ravens page: a prominent hero card right under the masthead that directly answers that question for the upcoming game, plus a season-long track record of every call made, styled and graded the same rigorous way as the main Accuracy Tracker.
- **Verdict logic** (`bet_verdict()` in `compute_ravens.py`): five discrete calls — **BET RAVENS**, **LEAN RAVENS**, **PASS**, **LEAN OPPONENT**, **FADE RAVENS** — driven by the same `engine.confidence_tier()` bands used everywhere else (Strong≥80%, Moderate≥65%, Lean≥55%, else Toss-up). Toss-up tier always resolves to PASS ("too close to call"). If a real market line exists for that game and the model/market gap is a "large disagreement" (≥15pts, same threshold as the existing value-bet framing), the verdict is **always PASS regardless of which side the model favors** — a gap that big is treated as more likely a model blind spot than a real edge, matching the site's established humble-model stance. Don't weaken this override to chase a "more exciting" answer.
- **Logging is idempotent and locked-in:** `compute_ravens.py` logs a call for every non-bye week the first time it's computed, and never overwrites an already-logged week's verdict/reasoning on subsequent runs — same "logged before the contest happens, never reworded after" integrity rule as the rest of the site. All 17 non-bye 2026 games were pre-logged in one pass since the full schedule + ratings were already available; a future session should only ever be *adding* new weeks (there usually won't be any, since the whole season logs at once) or *grading* completed ones, never rewriting an existing call.
- **Grading:** `grade_ravens_calls(bet_log, actual_results)` — pass `{week: actual_winner_team_name}` once a week's game is final. A call's recommended side "wins" if that side actually won; PASS calls are graded for record-keeping (what would have happened) but excluded from the win/loss record since no bet was recommended.
- **Track record display:** stat tiles (record, hit rate, flat-$50-per-call P&L using the same `wager_outcome`/`prob_to_american_odds` math as the main wager calculator, total calls logged) + a full table of every week's call, matchup, probability, and result (pending/WIN/LOSS/no-bet). Empty/pending state is expected and correct until games start.
- **Data:** persisted separately from the rest of `ravens_full.json` at `data/ravens_bet_log.json` (and `claude/ravens-bet-log.json` in the Project) so the log survives independently; `ravens_full.json` also carries a denormalized `bet_log`, `bet_track_record` (summary), and `this_week_call` (soonest upcoming logged call, i.e. what the hero card shows) for the page to consume directly.

## Persistent data store (lives in this Project — NOT in the sandbox, which is wiped between sessions)
- `claude/predictions-open.json` — every logged pick not yet graded (team-sport games use the schema in `log_predictions.py`; horse races use the schema in the horse-racing block, `league: "horse_racing"`).
- `claude/predictions-history.json` — `{"graded": [...], "rollups": {...}}`. Graded entries carry `correct`, `brier`, `actual_winner`. **Rotation policy (not yet automated — do this manually once the list gets large):** once `graded` exceeds ~1500-2000 entries, roll the oldest month into `rollups` (keyed `"YYYY-MM"`: `{n, correct, brier_sum}`) and drop the individual entries, so accuracy stats stay complete forever without the file growing unbounded. Project docs are size-capped.
- `claude/model-params.json` — current `home_adv`/`sigma`/`shrink_k` per league, plus `calibration_log` (append an entry each time `fit_home_adv_sigma` actually changes something: date, league, old/new values, n, old/new brier).
- `claude/ravens-data.json` — Ravens team/coaching/roster-changes/preseason/SB-odds-history/**roster** (roster is an object keyed by position group — "Quarterbacks", "Running Backs", "Wide Receivers", "Tight Ends", "Offensive Line", "Defensive Line", "Linebackers", "Defensive Backs", "Special Teams" — each a list of `{name, num, pos?, note?}`). This is the file to edit for any Ravens roster/coaching/preseason update.
- `claude/ravens-schedule.json` — the 18-week schedule with `week`, `opponent`, `location`/`neutral`/`site`, `date`, and `market_odds` where a real sportsbook line is known (currently Week 1 only — add more as they get posted). `compute_ravens.py` reads this + the NFL ratings to produce win probabilities; it does not need its own persistent "computed" file since it's cheap to regenerate each refresh — just persist `ravens-data.json` and `ravens-schedule.json` and re-run `compute_ravens.py`.
- `claude/ravens-bet-log.json` — the season's "should I bet this week?" call log (see feature section above). **Treat this one differently from the others**: don't regenerate it wholesale — `compute_ravens.py` reads it, adds only genuinely-new weeks, and (once you pass in actual results) grades existing entries in place. Write it back after every refresh so grading progress persists.

## Engine code (sandbox-local each session — reconstruct from this doc + the logic below if `~/sportspredict/` isn't there, e.g. on a fresh scheduled-task run)
Key modules (were at `~/sportspredict/` this session — a fresh session must recreate them, they're not large; **the actual, current versions of every one of these files are included in this export's `code/` folder — prefer copying those in verbatim over reconstructing from prose**):
- `engine.py` — `win_prob` (capped [0.03,0.97]), `shrink`, `make_pick`/`confidence_tier` (team sports), `grade_prediction`, `summarize` (accuracy rollups), `fit_home_adv_sigma` (calibration), horse-racing equivalents (`implied_prob_from_ml`, `field_probabilities`, `race_pick`, `summarize_horse`), and wager math (`fair_prob_to_vig_prob`, `prob_to_american_odds`, `american_to_decimal`, `wager_outcome`, `parlay_decimal_odds`) — the wager calculator's client-side JS in `dashboard.html` mirrors these functions exactly; keep them in sync if the math changes.
- `compute.py` — builds `data/predictions.json` (today's slate + picks) from the per-league CSVs + `model_params.json`.
- `compute_horses.py` — builds `data/horse_predictions.json` from `data/horse_racing_races.json` (race fields with morning-line odds).
- `compute_ravens.py` — builds `data/ravens_full.json` (= `ravens_data.json` + `roster` + a `schedule` array where each game gets `ravens_win_prob`, `model_odds`, and — where `market_odds` exists in `ravens_schedule.json` — a `value_bet` block comparing model vs. market with a plain-language "read" (agree / lean / **large disagreement**, the last one triggered at ≥15 points of edge and phrased to say a big gap is more likely a model blind spot — missing injury/coaching/roster context — than a real edge over Vegas; keep that humble framing, don't silently override the model to match the market)). Also computes a naive independent-games `expected_wins_naive` for the season, and — per the feature section above — builds/updates `data/ravens_bet_log.json` and merges `bet_log`/`bet_track_record`/`this_week_call` into `ravens_full.json` via `bet_verdict()`, `grade_ravens_calls()`, and `build_track_record()`.
- `grade.py` — `grade_open(actual_results: {pred_id: winner_name})` moves matured picks from open→history.
- `build_site_data.py` — assembles `predictions.json` + `horse_predictions.json` + accuracy summary (from `predictions-history.json`) into `data/site_data.json`, which gets embedded verbatim into `dashboard.html`'s `const DATA = ...` line. Also feeds the wager calculator's bet slip (built client-side from `DATA.leagues[*].games` + `DATA.horse_racing.races`) and bankroll simulator (`DATA.accuracy.graded_log` / `graded_log_horse`).
- `dashboard.html` (delivered as `index.html`) — the public page. Four views (nav.primary, numbered 01-04): Picks (per-league tabs), Horses, Track Record (accuracy tracker), Odds & Bets (wager calculator). Disclaimer banner is a fixed top strip — never remove it. Links to `ravens.html` via a banner under the masthead and a footer link.
- `ravens.html` — the Ravens sub-page. Same disclaimer bar, its own masthead/back-link to `index.html`, the verdict hero card, schedule, bet-call track record table, roster sections. Data is embedded the same way as `dashboard.html`, via `const DATA = {...};` built from `data/ravens_full.json` — re-embed by finding the line starting `const DATA = ` and replacing it wholesale (a plain `re.sub` on the JSON string throws `bad escape \u` because of `\uXXXX`-looking sequences in JSON escapes; either use a **lambda replacement** `re.sub(pattern, lambda m: json_str, html)` or, simpler, locate-and-replace the exact line as done for this feature).

## Daily refresh procedure (what the scheduled task should do each run)
1. **Pull state:** `project_read` `predictions-open.json`, `predictions-history.json`, `model-params.json`, `ravens-data.json`, `ravens-schedule.json`, `ravens-bet-log.json`. If sandbox files from a prior run aren't present, recreate `engine.py`/`compute*.py`/`grade.py` per the logic summarized here (pure-Python, no exotic deps — reconstruct straightforwardly from the function names/behavior described above, or better, copy in this export's `code/` folder verbatim).
2. **Grade what finished:** for every open prediction whose `date` has passed, fetch the actual result. **Data-source lessons from building this (see below) matter here** — don't trust one big WebFetch on a large ESPN JSON endpoint; prefer Wikipedia season articles / CBS Sports standings / league-specific results pages, and cross-check row counts. Build `{pred_id: actual_winner}` and call `grade.grade_open(...)`. For any Ravens game that's now final, also build `{week: actual_winner_team_name}` and call `grade_ravens_calls(...)` so the bet-call track record updates.
3. **Recalibrate:** for each league with ≥25 newly-sufficient graded games since last calibration, call `fit_home_adv_sigma` against that league's full graded history and update `model-params.json` (log the change in `calibration_log`).
4. **Generate today's picks:** re-fetch current standings + the next slate of upcoming games per in-season league, and re-fetch the next major horse race's entries/odds if one is coming up (check NYRA/Saratoga-successor-meet schedule, TwinSpires/DRF/BloodHorse for fields+morning line — see lessons below). Run `compute.py` / `compute_horses.py` equivalents, then `log_predictions.py`-equivalent to append new open entries.
5. **Refresh the Ravens page:** check whether a new week's market odds have posted for the upcoming Ravens game (add to `market_odds` in `ravens-schedule.json` if so — this is what powers the value-bet comparison, and can flip a week's verdict to PASS if it creates a large disagreement) and whether there's roster/coaching/injury news worth updating in `ravens-data.json` (roster_changes, preseason_standouts/concerns once the season starts, super_bowl_odds_history — append a new dated entry rather than overwriting). Re-run `compute_ravens.py` (which also handles bet-call grading per step 2 and idempotent logging) and re-embed into `ravens.html`.
6. **Rebuild + publish:** run `build_site_data.py` equivalent, re-embed into `dashboard.html`. Publish via the Artifact tool: for `index.html`, `url: https://claude.ai/code/artifact/203f9518-2fc3-4e03-8fe5-bfcae704173a`; for `ravens.html`, `url: https://claude.ai/code/artifact/e4d76eee-dbc4-4942-b4c0-89816dae746e` (**must pass `url`** on both so they update in place rather than creating new artifacts) — and remember to publish the absolute-cross-link copies (see the note at the top of this doc), not the relative-link bundle copies. Rebuild the zip bundle (`index.html` + `ravens.html` with relative links + `data/*.json` including `ravens_bet_log.json` + README) and `SendUserFile` it so the user has the latest to drop into their site (until/unless a folder is connected for direct commits).
7. **Write back state:** `project_write` the updated `predictions-open.json`, `predictions-history.json`, `model-params.json`, `ravens-data.json`, `ravens-schedule.json`, `ravens-bet-log.json` back to the Project.
8. Keep the message to the user short: what got graded (record so far), what's new today, any calibration changes, anything new on the Ravens page (including this week's bet-call verdict and any newly-graded results), and the refreshed file.

## Data-source lessons (important — learned the hard way in the v1 build)
- Cloud sandbox `bash` has **no general internet egress** (only pypi/npm/github API) — confirmed by testing. All external data must go through `WebFetch`/`WebSearch`.
- **ESPN's hidden JSON API** (`site.api.espn.com/apis/...`) is reachable via `WebFetch`, but for a *large* payload (full 30/32-team standings) the content gets **truncated before the model even sees it** and it will confidently return partial data claiming completeness. Cross-check row counts; don't trust one big call.
- **Wikipedia season articles** and **CBS Sports standings pages** fetch cleanly and completely — prefer these for full-league standings.
- ESPN JSON scoreboard endpoints are fine for **small** payloads (a day/week of games).
- `www.espn.com` HTML pages are client-rendered and return empty via WebFetch — don't use them. For NFL roster pulls, `nfl.com/teams/<team>/roster` and `lineups.com`'s depth-chart pages fetched cleanly where ESPN's roster page came back empty.
- **Horse racing:** Equibase blocks WebFetch (403). Race-preview/picks articles from outlets like TwinSpires, NYRA's own stakes-schedule pages, and BloodHorse reliably carry full fields with post positions, jockeys, trainers, and morning-line odds for major graded stakes in the days leading up to the race. NYRA's stakes-schedule page is a good source for "what's the next major race" lookahead.
- **Never run git through the device bridge on this repo.** An earlier session's attempt to commit/push via `device_bash` left `.git/` with a stale `index.lock` (plus several `.stale`/`.stale2`/`.stale4` copies of it) after being interrupted mid-write — device_bash can't delete or replace lock files there, so it couldn't self-heal, and it blocked GitHub Desktop from committing until Zak manually `rm`'d the lock files in Terminal. Scheduled refreshes should only ever write plain files into the working tree (as this doc's daily refresh procedure describes) and leave all git operations — including any lock cleanup — to Zak in GitHub Desktop / Terminal.
